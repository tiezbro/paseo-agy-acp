# paseo-agy-acp v2.0.0.0 最终方案

状态：已确认的开发基线。Admission 默认关闭；安装、切换 connector、真实 provider
测试、生产启用、tag 和发布仍需单独批准。

## 1. 这次迭代只解决什么

同一个 Antigravity 账号会被多个本地 Paseo Agent 同时使用。旧 connector 会让这些
请求各自直接启动，容易造成并发失控、集中启动和 503。本次只在
`paseo-agy-acp` 内增加一个所有 connector 共同使用的 Admission Controller：先排队，
获得席位后再运行原有 Antigravity turn。

它不修改 Paseo、不修改官方 `agy`、不管理 Agent 生命周期，也不保证官方 provider
永远不返回 503。它能保证的是：本地不会主动放大并发；不确定是否已经执行的业务
prompt 不会被自动重放。

## 2. 仓库只有两个源码功能区

```text
/home/tiezbro/projects/paseo-agy-acp/
|-- ACP Connector/
`-- Admission Controller/
```

- `ACP Connector/`：Paseo/ACP 协议、session/conversation 映射、Antigravity 进程、
  stream-json/SQLite、权限、取消、恢复协调和错误分类。
- `Admission Controller/`：共享席位、全局队列、启动速率、lease、heartbeat、崩溃
  槽位回收、provider cooldown 和排队进度。

package 入口属于 `ACP Connector/`，不是第三个功能区。Admission Controller 不得
导入 ACP、Antigravity CLI、conversation SQLite 或客户端通知实现。

Admission 数据库固定为 `shared-admission-queue` v1，只允许
`turn_requests`、`leases`、`cooldowns`、`turn_payloads`、
`lease_process_identities`、`start_history`、`sessions`、`events` 和
`schema_migrations`。旧 outbox、delivery claim 或 recovery claim 表均不属于最终
方案，出现时必须 fail closed。

## 3. 固定业务参数

| 项目 | 最终值 |
| --- | ---: |
| 同一账号最大活动 turn | 默认 3；运行时只允许整体降为 1 |
| 同时进入启动阶段的 turn | 1 |
| 两次启动的最小间隔 | 2 秒 |
| 最长排队时间 | 30 分钟 |
| 无 server wait 信息时的 503 cooldown | 30 秒 |

席位是同一 OS 用户、同一 `AGY_ACP_STATE_DIR` 下所有 connector 和模型共享的账号级
总量。不能通过换模型或启动第二个 connector 得到额外席位。合法值只有 `3` 和 `1`；
`2`、`4`、`5` 以及其他值必须拒绝。

一个 `AGY_ACP_STATE_DIR` 只服务一个 Antigravity 账号。Admission 启用期间禁止在线
login/logout；换号前必须先排空队列、等待活动 turn 结束并停止 Connector，再为新账号
使用独立的 `AGY_ACP_STATE_DIR`。当前 AGY 没有可信账号 ID，因此不伪造账号指纹。

## 4. 一条消息的完整流程

1. 用户消息先取得当前 session 的本地 turn 顺序权，再进入共享队列。
2. 队列记录请求、parent、模型和进入时间；业务 prompt 加密保存。
3. Admission Controller 只把当前最老且符合条件的请求交给对应 connector。
4. connector 取得 lease 后等待全局启动间隔，再启动原有 Antigravity turn。
5. turn 运行期间继续使用现有 conversation SQLite 和 ACP 更新链，不增加第二套
   live 输出、shadow parity 或 reconnect replay。
6. connector 定期更新 lease heartbeat。heartbeat 过期只表示“需要核验”，不等于
   可以直接释放席位。
7. provider 明确结束后，先记录结果，再立即释放席位；Paseo 负责 Agent 完成通知和
   归档。
8. 同一 Agent 后续再发消息时，重新进入共享队列。

空闲 session 和空闲 ACP 连接不占 turn 席位，也不为排队保留 resident PTY。关闭或
删除 session 时，尚未开始的排队请求会取消并删除 prompt；正在运行的 turn 走现有
取消流程，只有确认进程/终态后才释放席位。

## 5. 队列顺序

调度顺序是 oldest-eligible，并带 agent fairness；这里的 agent key 是启动时注入的
`PASEO_AGENT_ID`：

- 没有活动 turn 的 agent，优先于已经占用席位的 agent；
- 同一优先层内，先进入队列的请求先启动；
- 被 cooldown、已取消或已超时的请求不会堵住后面的可运行请求；
- connector 只能领取 Controller 当前选中的请求，不能点名越过队首；
- 每个 session 仍保持原有单 turn 顺序，避免同一 conversation 并发写入。

排队超过 30 分钟时，请求进入 `queue_timeout`，加密 prompt 在同一事务中删除，只保留
不可自动重放的终态记录。用户若仍要执行，必须发送一条新的消息并重新排队。

## 6. 503 和其他失败

- 只有可信的 `503 + UNAVAILABLE/MODEL_CAPACITY_EXHAUSTED` 才分类为
  `provider_capacity`，对应 provider/model 暂停 30 秒。
- cooldown 只影响哪些请求当前可启动，不增加或占用席位。
- connector 不做外层业务 prompt 自动重试。官方 CLI 内部若有自己的重试，仍属于
  同一个 turn 和同一个 lease。
- 429 quota、认证、权限、超时和 transport 错误分别保留类型，不把它们都伪装成
  503。

## 7. heartbeat、取消和崩溃

- 活动 lease 必须有 heartbeat；过期后只能标记 owner 可疑。
- 只有同时核对 connector 身份、child 进程身份和残留进程，才能决定槽位是否已经
  空闲。PID 存在或不存在本身都不够。
- 明确证明 prompt 尚未发送时，可以结束该请求并释放席位，但本版本仍不自动重放。
- prompt 可能已经发送、进程状态不明或 provider 终态不明时，请求进入
  `recovery_required`；不得重新发送业务 prompt。
- 明确证明本地进程树已经退出后，可以释放本地席位，同时保留
  `recovery_required` 供人工确认结果。
- 排队取消直接删除 payload；运行中取消沿用 connector 的 SIGINT/终态确认流程。

## 8. 排队进度和连接边界

等待中的请求可收到当前位置、可运行位置、已等待时间和 cooldown 截止时间。进度是
观察信息，不是新的业务消息，也不能改变调度顺序。

ACP 连接只负责当前在线 turn 的更新。连接断开不会触发 provider turn 重放，也不增加
terminal reconnect replay、Connector 自有 outbox claim store 或补偿归档。Paseo 0.4.0
继续独占 Agent 创建、等待、完成/错误通知、review、archive 和生命周期。

## 9. 明确不做

- 不支持 `2`、`4`、`5` 或其他席位配置；只支持默认 `3` 与保守模式 `1`；
- 不开发第二套 live parity、shadow comparison 或 terminal reconnect replay；
- 不开发 Agent 自动归档、10 分钟补偿归档或第二套委派账本；
- 不引入 MAACS Stage 2 门禁、生产 runtime 同步或 heartbeat supervisor；
- 不修改官方 Paseo、官方 Antigravity provider、账号、endpoint 或凭据；
- 不把测试通过、源码提交、安装、真实验收和生产启用混为一件事。

## 10. 结案门禁

1. 默认关闭时，原有 connector 行为和测试必须保持不变。
2. 启用时，多个 connector 必须共享同一个 3 席位池、单启动和 2 秒间隔。
3. agent fairness、30 分钟超时删除 payload、503 cooldown 和排队进度必须有确定性
   测试。
4. 取消和崩溃测试不得出现重复 provider dispatch；不确定 prompt 必须停在
   `recovery_required`。
5. provider 明确终态后必须立即释放席位，空闲 session/连接不得占席位。
6. `npm run validate`、架构边界和敏感信息扫描必须通过。
7. 最后才可在隔离 Paseo `127.0.0.1:6768` 运行真实 single canary；未经单独批准不得
   访问生产 `127.0.0.1:6767`、安装、切换、push、tag 或发布。
