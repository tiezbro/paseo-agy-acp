# Paseo Agy ACP v2.0.0.0 Admission Controller

Status: approved as the source-development baseline; not approved for runtime
installation, real-provider testing, production cutover, tagging, or release.

## 1. Objective

Add an Admission Controller inside paseo-agy-acp. It coordinates all local
connector processes before they start an Antigravity CLI turn. It is not a
second ACP connector, a remote gateway, an endpoint proxy, or a credential
broker.

~~~
Paseo Agent
  -> ACP Connector
     -> per-session TurnScheduler
     -> Admission Controller
        -> runtime.sqlite
        -> queue, capacity, starts, cooldowns, leases
     -> official agy process
~~~

The controller removes local unbounded concurrency, cross-process JSON races,
error flattening, and outer blind retry. It cannot guarantee that an official
provider will never return 503.

## 2. Scope And Honest Guarantee

Within one host, one OS user, one AGY_ACP_STATE_DIR, and only v2 connectors,
the connector guarantees that it never automatically repeats an ambiguous
business prompt. A turn with unproven dispatch or termination becomes
recovery_required and remains queryable.

The connector cannot offer exactly-once execution across arbitrary crashes:
the CLI does not expose an idempotency key, transactional prompt dispatch, or a
reliable remote turn-status query. The controller must prefer a visible,
conservative recovery state over duplicate execution.

Out of scope:

- changing official Paseo, official agy, endpoints, or credentials;
- pooling identities across users or hosts;
- auto-retrying a business prompt after capacity, process, or delivery error;
- silently changing model, effort, or permission mode;
- replacing SQLite with stream-json before version-specific parity passes;
- archiving Paseo Agents from the connector.

## 3. Admission Policy

The source-development defaults are intentionally conservative. They remain
disabled configuration, not an approved production setting or an implicit
promise about provider capacity.

| Policy | Default |
| --- | ---: |
| maxActiveTurns | 2 |
| maxConcurrentStarts | 1 |
| minStartInterval | 2 seconds |
| maxResidentPtys | 1 |
| maxAuxiliaryAgyProcesses | 1 |
| queueTimeout | 30 minutes |
| startTimeout | 30 seconds |
| heartbeatInterval | 2 seconds |
| ownerSuspectAfter | 10 seconds, observe only |
| capacity cooldown without server wait | 30 seconds |

`maxActiveTurns=2` remains unapproved for runtime use until an isolated
acceptance run passes. Later values 3, 4, and 5 require separate evidence and
approval. Capacity is first limited by an auth-context total, then by
provider/model cooldown; model limits must never add up to more than the
auth-context total.

## 4. Durable State

AGY_ACP_STATE_DIR/runtime.sqlite is a local SQLite WAL database. Schema v10 is
the current source-development contract. The state directory is mode 0700;
the database, WAL, key material, and backups are mode
0600. Connections use synchronous=FULL, busy_timeout, short write
transactions, and a local reliable filesystem only.

| Table | Purpose |
| --- | --- |
| sessions | ACP session, Paseo agent, conversation, cwd, roots, model, effort, mode, project, cursor |
| turn_requests | immutable request metadata, queue order, deadline, execution state, outcome |
| turn_payloads | encrypted content blocks, nonce, key version, TTL |
| leases | generation, phase, owner instance, PID/process identity, heartbeat |
| lease_process_identities | fenced Linux connector/child identity bound to one lease generation |
| delivery_outbox | stable event ID, encrypted ACP update, delivery state |
| delivery_claim_leases | payload-free owner/generation/heartbeat fence for ACK delivery |
| cooldowns | auth context, provider, model, reason, notBefore, evidence source |
| start_history | start-rate accounting |
| agy_startup_permits | fenced cross-process auxiliary and resident-PTY ownership |
| events | sanitized state transitions and HMAC correlation only |
| schema_migrations | schema and cutover history |

Prompts, tool arguments, raw streams, headers, and credentials must not appear
in argv, environment variables, logs, events, ordinary hashes, or reports.
Payloads and undelivered ACP updates use authenticated encryption. Correlation
values use a local keyed HMAC, never a raw prompt hash.

## 5. Request Identity And Delivery

When ACP exposes a stable clientMessageId, define:

~~~
requestId = HMAC(agentId | acpSessionId | clientMessageId)
~~~

(acpSessionId, clientMessageId) is unique. The same request and fingerprint
reconnects to its existing waiter or terminal outcome; the same ID with a
different fingerprint is rejected into recovery_required; a new ID is a new
business request even if its text matches an earlier request.

If a path cannot supply a stable client message identity, it may execute while
its process is alive, but it cannot participate in automatic crash recovery.

Each outbound ACP update has a stable event ID derived from its conversation,
cursor, event type, tool ID, and state. The outbox writes pending delivery
before notifying the client and marks delivered only after the chosen protocol
acknowledgement. If Paseo cannot prove that repeated IDs are idempotent, an
unconfirmed update stays recovery_required; it is not automatically replayed.

## 6. Execution State Machine

~~~
queued -> admitted -> starting -> dispatch_intent
     -> active | dispatch_ambiguous -> provider_terminal -> released

not_started -> delivery_pending -> delivered | recovery_required
cancel_requested -> terminating -> cancelled | recovery_required
~~~

Execution capacity and delivery are separate. A confirmed provider terminal
state can release an execution slot while the result remains in the delivery
outbox. Ambiguous dispatch, unproven cancellation, a lost conversation, or
unfinished background work remain recovery_required and retain their unknown
capacity debt.

The dispatcher obtains the per-session TurnClaim before queue admission. It
must never hold a global lease while waiting for a local session slot.

1. Encrypt and persist the request, then enqueue it.
2. Atomically select the oldest eligible request under fairness and cooldown.
3. Create an admitted reservation and then a start permit.
4. Spawn agy without placing prompt text in argv.
5. Atomically persist PID/process identity and fsynced dispatch_intent under the
   current lease generation. Exact replay is idempotent; conflicts fail closed.
6. Revalidate generation and cancellation synchronously. A failed revalidation
   does not erase the already durable intent and cannot make the request
   automatically replayable; it enters `dispatch_ambiguous` even when no prompt
   byte was written.
7. Confirm the exact atomic intent record, then write the prompt to stdin in
   the same synchronous stack.
8. Observe provider activity, persist cursor and session binding, then enter
   active.
9. Persist the terminal provider outcome before releasing confirmed capacity.
10. Create and deliver the outbox event without replaying the provider turn.

The stdin or fresh-PTY path is a version-specific capability. The exact
supported agy launcher must pass a dedicated fake-child canary before it is
enabled. Canary prompt correlation uses a purpose-separated local HMAC key;
plain prompt hashes are forbidden. Failing that canary is a release blocker;
the connector must not fall back to prompt argv.

## 7. Recovery And Cancellation

| Condition | Required behaviour |
| --- | --- |
| queued crash | retain encrypted payload; reconnect only by the same request ID |
| queue timeout | delete the encrypted payload atomically, retain the terminal request record, and never auto-replay the same request ID |
| starting without dispatch_intent | after proven owner death, terminate residue and safely requeue |
| after dispatch_intent, before provider observation | dispatch_ambiguous; never replay |
| active process alive | retain lease and monitor |
| process exited with background work unproven | retain unknown capacity debt |
| provider terminal, delivery unproven | release execution capacity; recover delivery from outbox |
| conversation or remote terminal unprovable | recovery_required; manual resolution required |

Heartbeat expiry only marks an owner suspect. It is not permission to reclaim an
active lease. Process identity includes PID, start time, boot identity, process
group, and connector instance ID; PID alone is insufficient.

Connector startup is guarded by a one-shot, observation-only recovery barrier.
It reads payload-free nonterminal dispatches, active session bindings,
controller-owned outbox claims, auxiliary/resident startup permits, and Linux
process residue in one decision. A missing source, invalid row, duplicate,
partial fence, owner mismatch, untracked process, or any pending recovery item
blocks dispatch. The barrier has no decrypt, signal, release, requeue, claim,
or provider-start capability, so it cannot turn uncertainty into replay.

Linux process lifecycle code is likewise observation, recovery, and
cancellation only. It has no provider-start or prompt-write method. The
dispatcher and its SQLite-primary adapter are the sole production path that
can cross the irreversible business-prompt boundary.

Controller exception messages omit durable request, delivery, and lease
identifiers. Callers distinguish failures through typed errors and durable
state rather than copying correlation identifiers into free-form diagnostics.

Queued cancellation revokes queue eligibility and deletes payload. A dispatched
turn receives SIGINT and waits for process plus conversation/background terminal
evidence. Escalation to process-tree termination or a lost conversation does
not prove cancellation: it enters recovery_required. Only an official
CANCELED/INTERRUPTED or equivalent verified state produces cancelled.

## 8. Coverage, Fairness, And Errors

Every local agy start passes the startup gate: new, continuation, restore,
follow-up, supervision PTY, agy models, authentication probes, login/logout,
model-cache refresh, and recovery processes. Model turns consume active
capacity; auxiliary work consumes only an auxiliary/start permit; idle
supervision PTYs consume a resident-PTY permit.

`auxiliary` and `resident_pty` permits are persisted in SQLite and fenced by
owner plus generation. They use independent cross-process capacity limits.
Heartbeat expiry is reported by recovery inventory but never deletes or
reassigns a permit. The source-only production graph owns one startup launcher;
the dispatcher, AcpAgent-facing startup surface, and recovery barrier must all
use that exact instance so a second in-memory or caller-supplied queue cannot
bypass admission.

Scheduling chooses the oldest eligible request. With multiple parents queued,
a parent with active work does not overtake a parent with none. Cooldown,
cancellation, and expiry never make a blocked queue head prevent eligible work.

Classify errors in this order: structured SQLite provider error, stream-json
terminal result, official CLI exit/signal, connector transport/timeout. Map
503 plus UNAVAILABLE or MODEL_CAPACITY_EXHAUSTED to provider_capacity; map 429
plus QUOTA_EXHAUSTED to quota. Preserve only sanitized code, status, reason,
and HMAC correlation. Internal CLI retry holds its original lease.
wait_not_idle is only a lifecycle observation and cannot overwrite a provider
error.

## 9. Output And Lifecycle

v2.0 keeps conversation SQLite as the online source of truth. v2.1 parses
stream-json only as a shadow source and compares conversation identity,
messages, tools, files, subagents, background tasks, usage, cancellation, and
terminal errors. Shadow mode sends no duplicate ACP notifications. It becomes
an unattended primary only after exact-version, platform, and DSP parity
passes; SQLite remains recovery and drift evidence.

The controller releases a confirmed turn slot immediately, but the connector
remains until official ACP close/archive. MAACS/Paseo own parent notification,
result reclamation, create-time autoArchive, and any future ten-minute
compensating archive. Connector v2.0 does not archive Paseo Agents.

The serialized outbox pump first sweeps expired controller-owned claims, then
performs bounded pending delivery. A successful wire send remains
`awaiting_ack`; it does not deliver another copy of the same claimed event and
does not replay the provider turn. ACK settlement and provider-terminal plus
outbox creation are atomic SQLite transactions. Test-only fault seams verify
that a crash at either transaction midpoint leaves request, lease, outbox,
claim, and sanitized event state entirely at the prior durable state.

## 10. Migration, Rollback, And Release

Preflight strictly parses legacy sessions.json; parse failure is never an empty
store. Before migration, all v1 connectors and active agy processes must be
drained or officially closed. The migration transaction creates a verified
backup, imports session/conversation/cursor/model/effort/mode/cwd, and records
cutover_committed=false. models.json is cache-only and rebuilt.

Before the first v2 turn, rollback may use untouched legacy JSON. After a v2
turn, rollback is only to a v2-compatible binary that reads the same SQLite
schema. Direct return to v1 JSON is forbidden; an approved, drained reverse
export is a separate operation. Old and new connectors must never coexist in a
way that lets v1 bypass admission.

The source contains an asynchronous production graph builder, but the installed
`composeAcpRuntime()` entrypoint still rejects enabled Admission configuration.
The graph exposes a prompt surface only after exact request identity and ACK
negotiation, authenticated fresh-PTY configuration, complete bridge creation,
and an empty startup recovery barrier. A real version-specific fresh-PTY
launcher certificate and isolated provider acceptance remain unresolved release
gates.

The package version, tag, installation, symlink switch, daemon restart, real
provider test, push, and production use remain separately approved actions.

## 11. Delivery Phases And Gates

v2.0.0: SQLite state, encrypted payloads, admission, all startup coverage,
cancellation, typed errors, migration, rollback, fake-provider and OS-process
tests.

v2.1.0: stream-json shadow, exact-version parity, and delivery idempotency
gate.

v2.2.0: MAACS result reclamation and approved lifecycle automation.

The v2.0 acceptance matrix requires multi-process contention, fault injection
at every transaction/spawn/stdin/result/notify boundary, cancellation in every
phase, migration and rollback, sensitive-data scans, and an isolated Paseo
127.0.0.1:6768 lifecycle proof. Any duplicate provider dispatch, unproven
capacity release, lost session cursor, sensitive-data leak, or error flattening
is a failure. Official 503 may occur but must be accurately classified.
