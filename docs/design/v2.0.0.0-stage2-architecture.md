### 5.4 删除测试结论

- 删除 `AdmissionTurnCoordinator` → 排队/lease/恢复复杂度散布到 5 个 prompt 入口 → 深度成立。
- 删除 `composeAcpRuntime` → 组合逻辑散布到 `main.ts`/`runAcp`/测试 → 位置正确。
- 删除 `AgyPromptFreeDispatchBoundary.run` → accepted/ambiguous 语义消失；生产仅保留 `TurnDispatchBoundary` hooks 包围单次 stdin 写（`cli.ts:1132-1142`），无三态结果映射 → **Stage 3 SHALL 生产接线**（§17-2）。
- 删除 `startup-recovery.ts` → 启动期槽位回收消失 → 保留，但**运行期 reaper 必须新增**（§17-4），两者互补。

### 8.3 共享 `sessions` 表的跨区数据契约

- **Owner**：schema 所有权归 Admission（`schema.ts` + `controller.migrate()`）；行数据读写归 Connector 区 `SQLiteSessionStore`。
- **约束**：Admission 侧 `assertAdmissionSchemaIntegrity` 校验 `sessions` 存在且列/索引精确（`schema.ts:266-279`）；Connector 侧 `resolveSessionTableLayout`（`sqlite-store.ts:240-243`）+ `assertCanonicalColumns/Indexes`（:268-306）双重 fail-closed。v2 迁移不得改动 `sessions` 布局（§11.2 顺序明确）。
- **禁用**：Admission 不得把队列/席位/policy 状态写入 `sessions`；Connector 不得向 Admission 业务表 INSERT/UPDATE（现状 0 语句，保持）。

### 8.4 Event contract（审计事件）

`SanitizedAdmissionEvent`（`controller.ts:81-88`）：`eventSeq/kind/fromState/toState/occurredAt/correlationHmac`——identifier-free，不含 requestId/sessionId/payload/owner instance id；`events` 表由 `readSanitizedEvents` 分页读取（:777）。它是 audit-only 状态转移日志，**不能用于恢复 payload 或身份**，**不是** delivery ACK/outbox（§15）。`SanitizedEventKind` 13 种（:59-72）与 `transitionSignature` allowlist（:1493-1508）强绑定状态机；**v2 增加 4 种**（§8.2），仍 identifier-free。

### 8.5 Permission contract（一等契约 = REPAIR-002 修正 1）

**原则（Scheme §4.2 行 98「启动后继续走原有…权限…链」与 §4.7 行 159「启用后仍复用唯一的 ACP 在线输出路径」）**：权限链是 ACP Connector 的一等职责，Admission 不得要求用户进入 `dangerously-skip-permissions`，不得把进程 spawn 或 permission-key 交换当作业务 dispatch。

**当前违规（live 证据）**：

| 位置 | 现状 | 判定 |
| --- | --- | --- |
| `acp/session/setup.ts:44-49` | `admissionEnabled === true` 时强制 `config.mode === "dangerously-skip-permissions"`，否则抛错 | **偏离**（强制 bypass） |
| `acp/agent.ts:480-489` | `applyConfigOption` 在 `turnAdmission !== undefined` 时拒绝非 skip 模式 | **偏离**（强制 bypass） |
| `agy/cli.ts:535-541` | `admissionBoundary !== undefined` 时若 `promptInArgv || shouldUseInteractivePermissions()` → 抛 `admission_requires_prompt_free_print_mode` | **偏离**（交互 PTY 权限被整体拒绝） |
| `agy/cli.ts:540-542` | 交互权限需要 `onPermission` callback，但 admission 路径走不到 `runInteractivePrompt`（`cli.ts:546-548`） | **偏离**（权限面板不可达） |

**强制契约（Stage 3 SHALL，单一 disposition）**：

1. **删除**三处强制 `dangerously-skip-permissions`（`setup.ts:44-49`、`agent.ts:480-489`、`cli.ts:535-539`）；Admission 启用时用户可自由选择 `default`/`accept-edits`/`plan`/`dangerously-skip-permissions` 任一模式（模式枚举 `agy/cli.ts:217-228`）。
2. **唯一 fencing 点 = 第一次不可逆业务 prompt 写**：既有 `AgyAdmissionDispatchBoundary`（`cli.ts:289-293`）由 `TurnDispatchBoundary` 实现（`turn-coordinator.ts:299-364`）：`prepare → beforePromptWrite → [单次业务写] → afterPromptWrite`。`beforePromptWrite` 可 fail-closed 抛错（fence 失效即拒绝写）；`afterPromptWrite` 标记 active（`markActive`）。**进程 spawn、PTY 创建、permission-key 交换、`session/request_permission` RPC 都不经过该 fencing**——它们在同一个 turn/lease 内、位于业务写之前或之后，走既有 `onPermission` callback（`prompt.ts:463-474` v1 `requestPermissionV1`、`request-permission.ts:20/80`）与 ACP 客户端权限面板。
3. **PTY 路径**：`runInteractivePrompt`（`cli.ts:546-548`）在 admission 下必须可达——交互权限面板正常出现；`admissionBoundary` 的 `beforePromptWrite` 只在实际写入业务 prompt 时调用（交互模式下该写入点在 permission 通过后）。PTY permission-key 交换仍属 ACP/客户端所有，不是业务 prompt 写。
4. **Pipe 路径**：prompt-free print 模式（`--output-format stream-json` + stdin）的生产 dispatch 必须经 `AgyPromptFreeDispatchBoundary.run`（`dispatch-boundary.ts:119-181`）及其 result contract：`active → markActive`；`blocked`/`dispatch_ambiguous → markDispatchAmbiguous`；`writeAttempts ≤ 1`；零重试/零重放。
5. **不引入第三源码区、不为同一 fence 引入第二接口**：业务写 fencing 只有 `AgyAdmissionDispatchBoundary`（`TurnDispatchBoundary` 实现）一个 seam；不新增任何平行深接口（REPAIR-003 已删除此前提议的新接口设计）。**permission 决策本身仍归 ACP/客户端**（`request-permission.ts`、`session/request_permission`），Admission 不持有权限策略。
6. 测试：`tests/queue-steer.test.ts` 与 `tests/cli.test.ts` 增加 admission 下非 skip 模式的权限面板与业务写顺序断言（RED/GREEN receipt 见 §17-1/§20）。

## 11. Schema evolution boundary（F12 契约；REPAIR-002 修正 5）

### 11.1 版本与迁移台账

- **当前版本：`ADMISSION_SCHEMA_VERSION = 1`（`schema.ts:4`）→ Stage 3 SHALL 升为 `2`**。
- v2 台账：`MIGRATIONS = [{version:1, name:"shared-admission-queue"}, {version:2, name:"shared-admission-queue-v2"}]`。
- 迁移规则（`controller.ts:856-985` 既有）：`applied > 支持版本` 拒绝（:866-868）→ 未版本化业务表拒绝（:879-881）→ 全新库顺序执行 DDL → 写台账 → `assertAdmissionSchemaIntegrity`（:983）。
- **Stage 3 物理 ownership**：`S3-T18` 是 `Admission Controller/schema.ts` 与全部 v2 DDL 的唯一 writer；`S3-T02`/`S3-T06` 只消费 T18 已创建的 schema，分别实现 durable-policy 与 queued-owner 业务逻辑，不修改 schema 定义。

### 11.2 v1 → v2 单次前向迁移（顺序固定，逐版本 SQL 清单，禁止迁移框架）

0. **版本硬闸（在任何 DDL 之前）**：执行 `SELECT sqlite_version()`；若 `major.minor < 3.25`，抛 typed `AdmissionMigrationError` 并 fail-closed——数据库保持在 v1、不产生任何写入；不提供表重建回退路径。
1. `BEGIN`；PRAGMA foreign_keys=ON。
2. `ALTER TABLE turn_requests RENAME COLUMN parent_id TO agent_id`（SQLite ≥ 3.25 支持 `RENAME COLUMN`；硬闸已保证可用，**无重建回退分支**）。
3. `ALTER TABLE turn_requests ADD COLUMN queued_owner_instance_id TEXT NULL`；`ADD COLUMN queued_owner_recorded_at INTEGER NULL`。
4. `CREATE INDEX IF NOT EXISTS turn_requests_queued_owner ON turn_requests(queued_owner_instance_id) WHERE queued_owner_instance_id IS NOT NULL`。
5. `ALTER TABLE leases ADD COLUMN suspect_since INTEGER NULL`；`ADD COLUMN suspect_reason TEXT NULL`（CHECK 允许值）。
6. `CREATE TABLE policy_state (...)`（完整物理定义含 `policy_fingerprint TEXT NOT NULL`；§8.2；**空表，不播种**——由首个 v2 opener 原子认领，§11.3）。
7. `CREATE TABLE queued_owner_instances (...)`（§8.2 定义；空表）。
8. `INSERT INTO schema_migrations (version, name, applied_at) VALUES (2, 'shared-admission-queue-v2', ?)`。
9. `COMMIT`；随后 `assertAdmissionSchemaIntegrity`（v2 spec，含 `assertNoUnexpectedTables` 更新）。

**v1 存量库**：可前向迁移（步骤 0-9）或 fail-closed；**不得留在 v1 继续运行并声称支持新契约**。**v1 连接器读 v2 库**：`applied=2 > supported=1` → 拒绝（既有规则 :866-868）。**回滚边界**：回滚不得恢复 `parent_id`/`parentId` 或任何旧命名；`agent_id` 是唯一终态。

### 11.3 Durable policy 认领与一致性（F2/ADM-S04）

- `policy_state` 由迁移创建为空表；**首个 v2 opener** 以 `claimDurablePolicy(本地解析 policy, ownerInstanceId, now)` 原子认领（`INSERT ... WHERE id=1` 且 singleton CHECK，SQLite 事务保证恰好一个赢家；仿 `admission-key-store` 并发首建模式 `key-store.ts`）。认领时写 `policy_fingerprint` = HMAC(规范元组)。
- **后续每个 opener** 打开时 `assertDurablePolicyMatch()`：本地解析 policy 元组指纹 ≠ durable 指纹 → fail-closed 拒绝启动（`AdmissionRuntimeError`）；**不能各算各的，不能取较大值**（Scheme §4.1 行 88）。
- 显式 `1` 单 Connector 场景：首个 opener 认领 `max_active_turns=1`，后续同库 opener 必须同为 1——与「多 Connector 同库 policy 必须一致」一致。
- **policy 变更只能经控制接口**（`beginSoftDrainTo1`，§17-5），**不得**用环境变量就地改 durable policy（v1 的「每 Connector 各读各的」在 v2 终止）。
- **软排空状态机（单一终态元组）**：仅一条路径 `3 → soft_draining_to_1 → steady(max_active_turns=1)`。`beginSoftDrainTo1(requesterOwnerInstanceId, now)` 原子地把 `drain_state` 置为 `'soft_draining_to_1'`（同事务写 `policy_state` 并 journal `policy_drain_started`）；排空期间**不接纳新 turn**（`hasSeatCapacity` 返回 false）、**不杀 active turn**、queued 请求保持 queued（timeout/cancel/recovery 照常）。**完成条件 = `activeLeaseCount() === 0`**；完成时同事务把 `drain_state` 置回 `'steady'`、`max_active_turns` 置为 `1`、journal `policy_drain_completed`——**终态元组是 `drain_state='steady' AND max_active_turns=1`，满足 `drain_state` CHECK（仅 `'steady'|'soft_draining_to_1'`），终态绝不把 `drain_state` 写为数值 `1`**。所有 Connector opener 经 `assertDurablePolicyMatch` 观察同一元组。
- **明确反驳 test-contracts 的「policy 状态可不升版本」声称**：policy 的 durable 持久化、指纹一致性与软排空状态机是**已确认业务义务**（§4.1/§4.7），其物理载体（`policy_state` 表 + `suspect_since`/`queued_owner_*` 列 + 4 个新事件 kind）**必须经 v2 版本台账引入**；任何「v1 内扩展 policy 状态」的方案都违反 schema integrity guard 与版本语义，**不获准**。

### 11.4 完整性守卫（v2）

`assertAdmissionSchemaIntegrity`（`schema.ts:261-279`）= FK 开启 + **无意外表**（:281-291）+ 逐表/列/索引/FK/台账精确比对。v2 白名单 = 9 业务表 + `sessions` + `schema_migrations`（§8.1）。**任何新表/列/索引必须先登记并通过守卫**；无业务义务依据的新增表在规格与 review gate 拒绝（Controller Prompt 行 229）。**跨区影响**：`sessions` 布局由 Connector 侧 `sqlite-store.ts` canonical 校验，v2 迁移不动 `sessions`；若未来 v3 涉及 `sessions`，两区必须同 commit 对齐。
